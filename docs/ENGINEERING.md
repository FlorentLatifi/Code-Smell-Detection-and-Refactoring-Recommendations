# Engineering handbook

Operative rules for every change in this repository. Where a rule here conflicts
with a generic best practice, this file is the one that applies.

## 1. What this is

A static analysis system for **Java** that (A) detects code smells with metric
based rules, (B) detects them with a classifier trained on MLCQ, and (C)
proposes and applies **deterministic AST refactorings**, plus a web interface
over the three. It is simultaneously the artefact of a UBT bachelor thesis
(Florent Latifi, mentor Altina Salihu, submission ~November 2026), so the code
is not the only deliverable: every technical decision must survive being
written up and defended.

Hard constraints, not preferences:

- **Zero cost.** No paid API, no cloud tier requiring a card. Everything runs
  locally on a laptop with no dedicated GPU. Paid options stay out of scope,
  including as a recommended alternative.
- **Reproducible by a third party.** A committee member with a clean checkout
  must be able to regenerate every number in the Results chapter. Anything that
  cannot be regenerated by a script does not go in the thesis.
- **No LLM in the product path.** Refactorings are AST transformations, not
  generated text. This is a deliberate decision (see `docs/DECISIONS.md`), and
  reopening it requires a reason, not convenience.
- Thesis prose is **Albanian**; code, identifiers, docstrings and this file are
  **English**.

## 2. Architecture

One-way dependency chain. A module may import from its left, never its right.

```
parsing → model → metrics → detectors → { ml, refactor } → api → frontend
                                    ↘ evaluation ↗
```

Concretely:

- `model/entities.py`: plain data. No parsing logic, no metric logic, no I/O.
- `parsing/`: tree-sitter front end. Records **syntactic facts** only
  (bare names, `this.x`, `receiver.member`). It is deliberately not a symbol
  resolver; do not grow one here.
- `metrics/`: reads the model, writes `metrics` dicts. **Traverses each class
  once**; a new metric reuses the facts the parser collected instead of walking
  the tree again.
- `detectors/`: pure functions `(ClassInfo[, MethodInfo], Thresholds) -> Smell | None`.
  Every numeric threshold lives in `detectors/thresholds.py`, never inline,
  because the sensitivity sweep in the Results chapter mutates them
  programmatically.
- `ml/` and `refactor/`: consume detector output and the model. They do not
  import each other.
- `api/`: transport only, meaning validation, serialisation and error mapping. No
  detection or refactoring logic in a route handler.

Invariants that hold today and must keep holding:

- A detector returns the `Condition`s it evaluated, never a bare boolean:
  the UI explains *why*, the thesis reports which clause carried the detection,
  and severity is derived from measured excess rather than assigned.
- Refactoring names in `detectors/rules.py::REFACTORINGS` are the contract
  between detection and the refactor engine. Renaming one is an API change.
- Severity uses the MLCQ scale (`minor`/`major`/`critical`) so rule output
  compares to the ground-truth labels with no mapping step.

## 3. Thesis-grade invariants

These have no equivalent in a normal codebase and are the ones most easily lost:

1. **Every threshold and every metric definition traces to a citation.** If a
   number cannot be attributed to Lanza & Marinescu, Chidamber & Kemerer,
   Fowler, or a stated empirical calibration, it does not get committed. Put
   the source in the docstring next to the number.
2. **Never tune a threshold, a metric, or a detector to make a test pass.**
   Expected values in tests are derived by hand from the fixture. If code and
   test disagree, one of them is wrong; find out which before touching either.
3. **No data leakage in any evaluation.** MLCQ samples from the same repository
   must never be split across train and test. Use grouped splits keyed by
   project. A random row-level split inflates F1 and is exactly what a reviewer
   looks for.
4. **Report negatives.** A detector with poor recall, a smell the model cannot
   learn, a refactoring that fails preconditions half the time: these go in
   the thesis. Hiding them is worse than having them.
5. **Fixed seeds, pinned versions, recorded environment** for every experiment.
   Results land in `data/results/` as committed CSV/JSON, produced by a script
   under `scripts/`, never by hand.
6. **Decisions are logged as they are made**, in `docs/DECISIONS.md`. That file
   is the raw material for the Methodology chapter; reconstructing rationale
   three months later is how theses lose marks.

## 4. Refactoring engine safety

The engine rewrites the author's source. It is the only part of the system that
can destroy work, so it gets the strictest rules:

- **Refuse rather than corrupt.** Every transformation declares preconditions.
  If a precondition cannot be *proven* from the parse tree (an unresolved
  name, a possible side effect, an overload we cannot disambiguate), the
  transformation reports "not applicable" with a reason. A refusal is a correct
  outcome and must be counted in the results, not treated as a failure.
- **Compile-verified.** Every applied transformation is checked with `javac`
  against the project. It does not count as applied until it compiles.
- **Behaviour-checked where possible.** For corpus projects that ship a test
  suite, run it before and after. "Compiles and the project's own tests still
  pass" is the empirical claim the thesis makes; nothing weaker.
- **Never write in place by default.** Output to a copy or a patch. In-place
  modification requires an explicit flag and a clean working tree.
- Analysed code is **data, never executed**, except deliberately, in the
  verification step, for corpus projects the author chose.

## 5. Testing

- Unit tests carry **hand-derived** expected values with the derivation in a
  comment. Golden files generated from current output prove only that the code
  still does what it did.
- Every detector needs a positive fixture, a near-miss negative (satisfies some
  clauses but not all), and an edge case (interface, enum, empty class).
- Every refactoring needs: applies-correctly, refuses-when-unsafe, and
  output-compiles.
- Never delete, skip or weaken a test to get green. A pre-existing failure and a
  newly introduced one are different things and get recorded as such.
- Run `python -m pytest backend -q` before declaring anything done.

## 6. Web layer: real threat model

The relevant risks are resource and path handling, not authentication:
the app is single user and binds to localhost.

- **Path traversal / arbitrary read**: an analysis path is user input. Resolve,
  canonicalise, and confine it to an allowed root. Reject symlinks that escape.
- **Archive handling**: if a zip upload is added, cap entry count, total
  uncompressed size and per-entry path (zip-slip). Stream, do not load whole.
- **Resource exhaustion**: cap file size, file count and total analysis time.
  A pathological source file must not hang the server.
- **Subprocess use of `javac`**: fixed argument list, never a shell string,
  always with a timeout and a temporary working directory.
- **Error responses** carry a message and a code, never a stack trace or an
  absolute filesystem path.

Out of scope, and deliberately so: authentication, authorisation, multi-tenancy,
CSRF, rate limiting, secrets management, horizontal scaling, circuit breakers.
If one of these later becomes relevant, log the change in `docs/DECISIONS.md`.

## 7. Code standards

- Prefer the simplest solution that is correct. This codebase currently has no
  unnecessary abstraction; keep it that way. No design pattern without a
  concrete second use case.
- Type hints everywhere; `from __future__ import annotations` at the top.
- Docstrings explain **why**, not what. The existing modules set the standard:
  match their density and tone.
- Pure functions where the domain allows; parsing, measurement and detection
  stay side-effect free.
- No magic numbers outside `thresholds.py`.
- Dependencies are pinned exactly and added only when the alternative is
  writing something substantial ourselves. Every new one must be free,
  maintained, and permissively licensed.

## 8. Definition of done

Not "the code is written". A change is done when:

- [ ] the test suite passes and new behaviour has tests;
- [ ] hand-derived expectations, not generated goldens;
- [ ] thresholds and metric definitions cite a source;
- [ ] the layering in §2 is intact;
- [ ] anything empirical is regenerable by a script;
- [ ] a decision worth remembering is in `docs/DECISIONS.md`;
- [ ] `docs/ROADMAP.md` status is updated if a milestone moved;
- [ ] what was *not* verified is stated plainly.

A suite that was not run is not a suite that passed, and a check that was not
performed is not a verification. Neither gets written down as one.

## 9. Conventions

- Commit messages: Albanian, imperative, e.g. `Shto motorin e refaktorimit`.
- **No co-author trailers.** A commit carries one author, the thesis author.
  `Co-Authored-By:` lines are not added for any tool or assistant: this repository
  is submitted work, and the authorship shown on it is the authorship being
  examined. This overrides any tool default that adds such a line.
- Small, coherent commits. One concern each.
- `docs/ROADMAP.md` = what and when. `docs/DECISIONS.md` = why. This file = how.
- Generated data goes to `data/` (gitignored, except `data/results/`).
- Experiment entry points go in `scripts/`, never in module `__main__` blocks.
